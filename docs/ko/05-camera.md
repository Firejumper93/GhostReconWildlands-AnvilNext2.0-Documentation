# 05 - 카메라

이 문서의 모든 RVA는 별도 표기가 없으면 2017년 무렵의 리테일 빌드 기준입니다.

## 중요한 것은 이 함수 하나

**`UpdateCameraMatricesAndFrustum`**, 구현 RVA `0x0C5E47E0`, 썽크 `0x0135F720`.
Anvil VR 커뮤니티에서는 보통 이것을 `on_calc_mvp`라고 부릅니다. 인자를 **21개** 받고,
`rcx`가 카메라이며, 플레이어 카메라 기준으로 **프레임당 약 2회** 호출됩니다(측정값:
73,311프레임에 걸쳐 146,628회 호출).

`[VERIFIED]` 인자 매핑은 메뉴, 도보 이동, 느린 회전, 자유 비행 포토 모드에 걸쳐 전체 인자
스냅숏 55개로 런타임에서 확인했으며 **불일치는 0건**이었습니다.

| 인자 | 값 |
|---|---|
| 1 (`rcx`) | `cam` |
| 2 (`rdx`) | `cam + 0x290` |
| 3 (`r8`) | `cam + 0x314` |
| 4 (`r9`) | `cam + 0x334` |
| 5 ~ 11 | `cam + 0x324`, `cam`, `+0x360`, `+0x420`, `+0x4A0`, `+0x4E0`, `+0x520` |
| 12, 14, 15 | 부동소수점 (측정값 `0.8`/`0.846`, `0.1`, `0.2`) |
| 13 | `cam + 0x79C` |
| 16 | 카메라 구조체 바깥의 **포인터**, 대상 미확인 |
| 17 ~ 21 | `cam + 0x5A0`, `+0x560`, `+0x460`, `+0x5E0`, `+0x620` |

인자 6이 카메라 베이스 자신이라는 점에 주목하세요. 정적 분석에서 가장 의심스러웠던
부분인데, 표본 55개 중 55개에서 그대로 성립했습니다.

## 카메라 구조체

| 오프셋 | 내용 |
|---|---|
| **`+0x000`** | **카메라의 월드 트랜스폼, 64바이트. 실제로 유효한 그것** |
| `+0x290` | int, 카메라 모드/타입 열거값 |
| `+0x2A0` | `Matrix4x4*` `worldMatrixOverride` |
| `+0x2B0` | float |
| `+0x2BC` | float, 기본 시야각 |
| `+0x2C4`, `+0x2C8` | float, 투영 스큐 x, y |
| `+0x420 .. +0x620` | 4x4 행렬 아홉 개, `0x40` 간격으로 연속 |
| `+0x748` | 함수 진입부의 모드 변경 동기화 코드가 접근 |

### `worldMatrixOverride`는 `+0x2A0`에 있다

`[VERIFIED]` 오리진스 시기의 의사 코드에서 이식하는 중이라면, 그 코드는
`*(Matrix4x4 **)(pCamera + 576)`을 읽습니다. 와일드랜드는 같은 블록을 다른 오프셋에서
**명령어 단위로 동일하게** 재현합니다.

```
0x0C5E4844  mov rax, [rsi + 0x2a0]     ; rsi = pCamera. 오버라이드 포인터.
0x0C5E484B  mov rdx, [rbp + 0x4f]      ; = 인자 6 = 카메라 베이스
0x0C5E484F  test rax, rax
0x0C5E4852  je  0x0C5E4872             ; null이면 건너뜀
            movaps x4                  ; 64바이트 복사
0x0C5E4872  lea rcx, [rbp - 0x39]
0x0C5E4876  call ...                   ; -> 0x0CC28A10, 뷰 행렬 빌더
```

즉 오버라이드는 `+576`이 아니라 **`Camera + 0x2A0`(672)**에 있으며, 결정적으로 이 블록은
오버라이드 행렬을 **`Camera+0x000`으로** 복사합니다. 같은 패턴이 같은 구조체에 대해
`0x0C508FA7`에서도 독립적으로 나타납니다.

### `+0x420 .. +0x620`의 아홉 개 행렬

`[VERIFIED]`, 추측이 아니라 런타임 내용으로 식별했습니다. 행렬은 행 우선이며 이동 성분이
네 번째 행에 있으므로, **엔진은 행 벡터로 합성합니다**(`v * M`).

| 오프셋 | 인자 | 정체 | 근거 |
|---|---|---|---|
| `+0x420` | 8 | **투영** | 원근 형태, `[3][2] = 0.1` = near, `[2][3] = -1` |
| `+0x460` | 19 | 투영 변종 | x/y 스케일 동일, `[2][2] = -1`, `[3][2] = -0.1`. `[INFERRED]` near/far 깊이 분할의 원거리 절반 |
| `+0x4A0` | 9 | 카메라 포즈(월드) 행렬 | 정규 직교 행, 이동 행 = 카메라 월드 위치 |
| `+0x4E0` | 10 | 역투영 | 수치적으로 `+0x420`의 정확한 역행렬 |
| `+0x520` | 11 | 역 뷰-투영 | 행 단위로 `invProj * pose`와 일치 |
| `+0x560` | 18 | 역 뷰-투영, 두 번째 변종 | 행 0-1은 `+0x520`과 동일, 행 2-3은 부호 반전 |
| `+0x5A0` | 17 | **뷰-투영** | 열 3 = 카메라 전방 행의 부호 반전 |
| `+0x5E0` | 20 | `+0x420`의 사본 | 모든 덤프에서 동일 |
| `+0x620` | 21 | `+0x4E0`의 사본 | 모든 덤프에서 동일 |

`[INFERRED]` 프레임당 두 번의 호출은 깊이 분할의 각 절반에 하나씩 대응하며,
`+0x420`/`+0x460` 투영 쌍과 맞아떨어집니다.

## 어디에 쓸 것인가, 그리고 어디에 쓰면 안 되는가

이는 실험으로 결론이 났고, 부정 결과가 긍정 결과만큼 유용합니다.

`[VERIFIED NEGATIVE]` **`Camera+0x4A0`(포즈 슬롯)에 쓰는 것은 아무 효과가 없습니다.**
함수 진입부에서 초당 약 400회씩 15도 요(yaw)를 합성해 넣었더니 폴트도 0건, **시각적
변화도 0건**이었고, 주기적 덤프에서도 `+0x4A0`/`+0x5A0` 쌍은 깨끗하고 서로 일관되었으며
주입한 요의 흔적이 전혀 없었습니다. `+0x4A0`은 함수가 사용 전에 다시 써 버리는 **파생
출력**입니다.

`[VERIFIED]` **`Camera+0x000`에 쓰면 동작하며, 여기가 주입 지점입니다.** 같은 15도 요를
함수 진입부에서 루트 트랜스폼에 합성한 결과:

- 게임이 조준하는 방향에서 일정한 요만큼 어긋난 화면이 렌더링되며, 플레이 중 매우 잘
  보임
- **비조준 사격이 조준점 바깥에 명중**: 렌더링되는 화면은 움직이지만 게임의 조준은 그대로
  유효하게 남으며, 이는 카메라 모드에서 의도하는 분리 그 자체
- 회전이 누적되지 않음. 이는 엔진이 **매 프레임 자신의 카메라 상태에서 `Camera+0x000`을
  다시 만든다**는 것을 증명하며, 따라서 호출마다 합성해도 누적이 아니라 일정한 오프셋이
  됨
- 모든 파생 행렬(뷰-투영, 두 역행렬, `+0x4A0`의 포즈)이 주입된 포즈를 일관되게 따라갔고,
  루트와 파생값 사이의 요 차이는 0.00도로 측정됨

`[VERIFIED]` **포즈 슬롯은 완전히 일반적인 6DOF 방향을 받아들입니다.** 포토 모드에서 롤을
주는 동안 각 행은 임의의 정규 직교 기저를 담았고 렌더러가 그대로 따라왔습니다. 짐벌 제약도,
중력 기준 재직교화도 없습니다.

### 눈에 띄는 아티팩트 하나

`[VERIFIED, 관측됨]` 오프셋이 회전해 들어가는 쪽 화면 가장자리에서 **식생 컬링이
어긋납니다.** 식생 가시성은 `on_calc_mvp`가 회전을 적용하기 *이전에* 카메라를 소비하는
무언가가 결정합니다.

프레임당 변화량이 작으면 눈에 띄지 않습니다. 언젠가 문제가 된다면, 해결책은 포즈 쓰기를
프레임에서 더 이른 시점, 즉 `BeginFrame` / `UpdateCamera` 태스크 경계에 적용하는
것입니다.

### 프레임 멱등성

이 슬롯에 쓸 때는 증분 합성이 아니라, 프레임마다 한 번 캡처한 기준값에서 도출한 **절대**
값을 쓰세요. 프레임당 호출이 두 번인데, 엔진이 `Camera+0x000`을 각 호출 전에 갱신하는지
프레임당 한 번 갱신하는지는 확인되지 않았습니다. 절대값으로 쓰면 그 질문 자체가 무의미해
집니다.

## 어느 카메라가 플레이어의 것인가

`[VERIFIED]` **플레이어의 카메라는 `Camera+0x290`에서 `mode == 0`인 것입니다.**

`[VERIFIED]` **엔진은 카메라 객체를 여섯 개가 아니라 딱 두 개만 제공합니다.** 카메라가
교체되었을 법한 모든 상태에서 테스트했습니다. 도보, 차량, 조준, 조준경, 메뉴, 포토
모드입니다. 후기 Anvil 타이틀에서 물려받은 판별 방식은 상태마다 카메라가 하나씩 있다고
가정하므로 여기서는 애초에 통할 수가 없었습니다.

**포인터가 아니라 모드를 쓰세요.** 포인터 동일성은 안정적이지 않고 판별 기준도 아닙니다.

포토 모드는 연구 도구로 알아 둘 가치가 있습니다. 모드 0 카메라를 롤까지 포함해 캐릭터로부터
약 170m까지 자유롭게 날리며, 파생되는 모든 것이 그것을 따라갑니다. 무언가를 그 위에 쌓기
전에 카메라 쓰기가 완전히 일반적임을 공짜로 증명하는 방법입니다. (이 타이틀에서 자유 카메라는
게임 자체의 포토 모드이며 F10에 바인딩되어 있습니다. Ansel이 링크되어 있긴 하지만 NVIDIA
Ansel이 아닙니다.)

## 투영 함수 계열

`[VERIFIED]` 투영 함수는 하나가 아니라 **여섯 개**이며, 종횡비에서 fov를 계산하는
`0x0C510B20`의 선택기가 분배합니다.

| 썽크 | 함수 RVA | 형태 |
|---|---|---|
| `0x01347280` | `0x0C50C0E0` | `sub rsp,0x90`, `pInputVector`를 받음 |
| `0x01347460` | `0x0C50C2E0` | 작음, `sub rsp,0x40`, 입력 벡터 없음 |
| `0x01347530` | **`0x0C50C420`** | 큼, `sub rsp,0x100`, `rdx`에 추가 포인터 |
| `0x01347840` | `0x0C50C7E0` | |
| `0x01345720` | `0x0C5094D0` | |
| `0x01345800` | `0x0C509720` | |

`[VERIFIED, 측정으로]` **게임플레이 카메라는 `0x0C50C0E0`이 아니라 `0x0C50C420`을
사용합니다.** 잘 알려진 오디세이 시그니처와 바이트 단위로 일치하는 쪽이 `0x0C50C0E0`이라
가장 그럴듯한 후보로 보이지만, 그게 틀린 답입니다. 시그니처 일치가 정말로 완벽하기 때문에
분명히 짚어 둘 필요가 있습니다. 같은 함수인 것은 맞고, 다만 게임플레이 경로가 호출하는
함수가 아닐 뿐입니다.

이 함수의 다섯 번째 인자는 호출자 스택으로 전달되는 **수직 시야각(라디안)**입니다. 측정된
범위는 일반 플레이에서 0.78~0.87, 질주나 차량에서 약 1.22, 일반 조준(ADS)에서
0.49~0.52, 3배율 확대경 너머로 약 0.17, 메뉴에서 0.33 이상, 그리고 큐브맵 면 캡처(하늘 및
반사 프로브)에서는 정확히 pi/2(1.5708)입니다. 이 값을 오버라이드한다면 범위를 제한하세요.
큐브맵 캡처를 넓히면 하늘이 월드에 대해 미끄러집니다.

`0x0C50C0E0`은 여전히 지금 보고 있는 바이너리가 생각하는 그 바이너리인지 확인하는 데
유용한 **앵커**입니다. 시그니처가 이미지 전체에서 유일하기 때문입니다.

```
48 89 E0 53 48 81 EC 90 00 00 00 0F 29 70 E8 48 89 CB F3
```

## 보조 수학 함수들, 그 수학으로 이름 붙이기

| RVA | 정체 | 식별 방법 |
|---|---|---|
| `0x0C4DADE0` | `UpdateFrustumPlanesFromVPMatrix` | 뷰-투영 행렬에서 Gribb-Hartmann 평면 추출, 정규화 후 부호 반전. 호출 지점 11곳, 썽크 `0x013329A0` |
| `0x0CC28A10` | 뷰 행렬 빌더 | 네 행을 복사하고 한 행에 부호 상수를 곱한 뒤 역행렬을 호출. 카메라 월드 행렬을 넣으면 뷰 행렬이 나옴 |
| `0x05FE48C0` | 4x4 행렬 곱 | 브로드캐스트 셔플, `mulps`, 누산 |
| `0x06B1DBB0` | 4x4 역행렬 | `shufps`로 전치, 여인수 전개 |
| `0x0C510B20` | 투영 모드 선택기 | 종횡비에서 fov를 계산해 여섯 변종으로 분배 |

여기서는 함수를 문자열이나 추측이 아니라 그 산술이 무엇을 계산하는지로 이름 붙이는 편이
훨씬 견고합니다. 근거로 삼을 게임플레이 문자열 자체가 없기 때문입니다. 절두체 빌더가 좋은
예입니다. 이름을 알려 주는 것은 아무것도 없지만, 네 행에 대해 `m[row][0] + m[row][3]`을
계산하고 xyz 길이로 정규화한 뒤 부호를 뒤집는 함수는 그것 말고는 없습니다.

## 세션 하나를 날린 방법론 메모

**계속 변하는 부동소수점 값을 진단 테이블의 키로 삼지 마세요.** 초기 프로브는 서로 다른
인자 값마다 한 행씩 기록했는데, 매 프레임 바뀌는 부동소수점 값 하나가 몇 초 만에 테이블
전체를 소진했습니다. 정확한 값 대신 범위(최소/최대)를 누적하고, 테이블이 가득 찼는지를
항상 출력하세요. 자신의 한계를 보고하지 않는 용량 제한 프로브는 자신만만한 쓰레기를 만들어
냅니다. "이것이 가장 가까운 객체들"처럼 보이지만 실제 의미는 "이것이 어쩌다 테이블을 먼저
채운 객체들"입니다.
