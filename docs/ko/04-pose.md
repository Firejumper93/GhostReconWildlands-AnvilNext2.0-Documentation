# 04 - Pose 객체와 실제 본 레이아웃

캐릭터의 본이 실제로 어디에 있는지를 결정하는 엔진의 영역이며, 앞서 자신 있게 내린 답이
틀린 것으로 드러난 지점이기도 합니다. 아래에는 두 버전을 모두 남겨 두었습니다. 틀린 쪽도
초기화 코드에 대한 그럴듯한 해석이고, 다른 사람도 같은 결론에 도달할 것이기 때문입니다.

## 스켈레톤에서 애니메이션된 본까지의 연결 고리

`[VERIFIED]`, 서로 독립적인 세 가지 경로로: 별개의 리프 접근자 세 개 안에 있는 레이아웃
산술입니다.

```
Skeleton (0xCA0바이트)
  +0x010 -> 소유 ENTITY
  +0x120    완전한 {float4 T, float4 Q} 트랜스폼 (낡은 사본, 아래 참조)
  +0x1F0    스켈레톤 락
  +0x220 -> Rig 디스크립터        스켈레톤 클래스 단위로 공유, 트랜스폼은 없음
  +0x228 -> 리그 인스턴스
  +0x230 -> Pose A                애니메이션 출력
  +0x238 -> Pose B                최종 포즈 (+0x240과 +0x260에 별칭)
  +0x268, +0x270 -> Pose C, D
  +0xC7C    이름 맵 버전 스탬프
  +0xC90    비트 7 = 포즈 dirty

Pose (0x190바이트)
  +0x000 float4   루트 이동
  +0x010 float4   루트 쿼터니언   (그 w는 균일 스케일도 함께 담고 있음)
  +0x08C dword    플래그
  +0x090/+0x0A0   두 번째 트랜스폼 쌍, +0x160에 동반 dword
  +0x170 ptr      Rig (skel+0x220과 같은 객체)
  +0x178 ptr      본 트랜스폼 버퍼

본 버퍼, 노드 인덱스 i마다 스트라이드 0x20
  buf + 0x20*i + 0x00   float4 이동
  buf + 0x20*i + 0x10   float4 쿼터니언
```

## 레이아웃의 근거가 되는 접근자들

`[VERIFIED]` 각각은 단일 점프 썽크를 통해 도달할 수 있습니다.

| 대상 | 리테일 구현 | 리테일 썽크 | 업데이트 구현 | 업데이트 썽크 | 계약 |
|---|---|---|---|---|---|
| `Rig::BoneIndexFromNameHash` | `0x0A85F0F0` | `0x00CF90F0` | | | `u16(Rig* rcx, u32 crc32 edx)`, 실패 시 `0xFFFF` |
| `Pose::GetBoneRecord` | `0x0DC3F730` | `0x018BA4F0` | `0x0F1A51C0` | `0x018F00E0` | `buf + idx*0x20` 반환 |
| `Pose::GetBoneTranslation` | `0x0DC3F9C0` | `0x018BA500` | | | `void(Pose*, u16 idx, float4* out r8)` |
| `Pose::GetBoneRotation` | `0x0DC3FCF0` | `0x018BA550` | | | `void(Pose*, u16 idx, float4* out r8)` |
| `Pose::Bind` (버퍼 할당) | `0x0DC4DAA0` | | `0x0F1B55C0` | `0x018F3460` | `mov [rdi+0x178], rax` |
| `Pose::SetRootTransform` | | | `0x0F203FA0` | `0x01904570` | |
| `PoseCopy` (본만) | | | `0x0F1CC7A0` | `0x018FA690` | |
| `Skeleton::PoseRefresh` | | | `0x0F091720` | `0x018A09A0` | |
| `Skeleton::PublishAttachments` | | | `0x0F090D00` | `0x018A03B0` | |
| `Skeleton::MarkPoseDirty` | | | `0x0F080AA0` | `0x018996B0` | |
| `SkeletonPostUpdate` | `0x0DA1A990` | `0x01865A10` | `0x0F085A50` | `0x0189B430` | `rcx` = 스켈레톤 |

`GetBoneRecord`는 명령어 네 개 길이이며 스트라이드 문제를 완전히 정리해 줍니다.

```
movzx eax, dx
shl   rax, 5           ; x 0x20
add   rax, [rcx+0x178]
ret
```

`GetBoneRotation`은 레코드의 `+0x10`을 읽고, 아래의 플래그가 꺼져 있으면 `[pose+0x10]`의
루트 쿼터니언과 합성합니다. 이것이 레코드가 그 반대가 아니라 `{+0x00에 이동, +0x10에
쿼터니언}`임을 증명합니다.

이미지 전체에서 유일한 바이트 시그니처(리테일):

```
GetBoneRecord       0F B7 C2 48 C1 E0 05 48 03 81 78 01 00 00 C3
GetBoneTranslation  40 53 48 83 EC 30 48 8B 81 78 01 00 00
Pose::Bind          48 89 5C 24 08 57 48 83 EC 20 8B 81 8C 00 00 00
SkeletonPostUpdate  F6 81 92 0C 00 00 01 48 89 CF
```

## 공간: 월드가 아니라 모델

`[VERIFIED]` `skel+0x238`의 포즈는 생성 시 플래그 비트 26이 명시적으로 **꺼지므로**, 그
버퍼는 **모델 공간**에 있습니다.

```
월드 위치 = rootQ를 boneT에 적용한 뒤 rootT를 더함
월드 회전 = rootQ와 boneQ를 합성
```

엔진 자신이 정확히 이렇게 합니다. **루트 쿼터니언을 회전으로 쓰기 전에 정규화하세요.**
그 `w`가 균일 스케일을 담고 있기 때문이며, 이를 건너뛰면 스케일이 조용히 본 오프셋에
곱해집니다.

### `[pose+0x8C]` 플래그 비트

`Pose::Bind`에서:

| 비트 | 마스크 | 의미 |
|---|---|---|
| 26 | `0x04000000` | 본 버퍼가 이미 월드 공간에 있음. Pose B는 생성 시 꺼지며, 그래서 들고 있는 무기는 꺼진 상태로 읽힘 |
| 27 | `0x08000000` | 마지막 복사 이후 본이 변경됨 (솔버가 쓰고 나면 켜지고, `PoseCopy`가 끔) |
| 28 | `0x10000000` | 본 개수로 `[rig+0x34]` 대신 `[rig+0x36]`을 사용 |
| 24, 25, 29, 31 | | 고정 유지, `Bind`를 거쳐도 보존됨(마스크 `0xAF000000`). 25와 31은 `[UNKNOWN]` |
| 0..23 | | 전혀 사용되지 않으며 `Bind`가 마스킹해 버림 |

실제로는 늘 꺼져 있더라도 비트 26을 존중하세요. 언젠가 월드 공간 버퍼를 넘겨주는 경로가
생기면 이중 변환이 일어나는데, 이는 눈에 띄는 오류가 아니라 알아채기 어려운 미묘한
오류입니다.

## 엔진이 직접 보여 주는 예제

`[VERIFIED]` 리테일 `0x0A85B172`에서 엔진은 `edx = 0x89B93A80`(`LeftForeArm`의 CRC32)을
로드하고, 리그를 `rcx`에 넣고, 이름 조회를 호출한 뒤, 반환된 인덱스를
`GetBoneTranslation`에 넘깁니다. 그다음 `LeftHand`, `RightForeArm`, `RightHand`에 대해
같은 과정을 반복합니다.

이것이 엔진 자신이 보여 주는 표준 레시피입니다. **이름을 해싱하고, 리그에 대해 인덱스를
해석하고, 포즈 버퍼를 인덱싱한다.**

반복적으로 읽어야 한다면 `0x0DA15AE0`에 더 나은 템플릿이 있습니다. 캐시된 본 핸들
`{u32 nameHash +8, u16 nodeIdx +0xC, u16 stamp +0xE}`를 두고, 스탬프가 `[skel+0xC7C]`와
다를 때만 다시 해석하며, `[skel+0xC90] & 0x80`이면 포즈를 갱신합니다.

## 프레임 단위 체인

`[VERIFIED]` `SkeletonPostUpdate(skeleton)`은 순서대로 다음을 호출합니다. 도입부, 작업
함수(마지막에 Pose A를 Pose B로 복사), 컬링, 또 한 단계, `+0x238`에 루트 트랜스폼을
설정하고 다시 복사하는 함수, 그리고 두 개가 더 있습니다.

`[VERIFIED]` **`[[skel+0x238]+0x178] + idx*0x20`에 쓰는 것이 CPU 스켈레톤 쓰기이며, 이쪽이
실제로 유효한 편입니다.** 그 버퍼가 바로 세 접근자가 반환하는 대상이고, 이 접근자들은
애니메이션, 게임플레이, 그래픽에 걸쳐 34곳 이상에서 호출됩니다.

`[VERIFIED]` **`[skel+0x230]`(Pose A)에 쓰는 것은 무의미합니다.** 같은 업데이트 안에서
`+0x238`로 다시 덮어써지기 때문입니다.

`[VERIFIED]` **포즈 루트는 상태가 아니라 프레임마다 파생되는 사본입니다.**
`Pose::SetRootTransform`은 이미지 전체에서 `[pose+0x00]` / `[pose+0x10]`에 쓰는 유일한
코드이며(단일 히트 시그니처
`48 83 EC 28 0F 28 02 0F 29 01 0F 28 4A 10 0F 29 49 10 45 84 C0`), 소유 엔티티의 트랜스폼
노드 `[[skel+0x10]+0x18]`에서 값을 공급받습니다. 그 노드의 이동 성분은 `node+0x30`의 **네
번째 행**입니다. 반대 방향으로 되읽히는 일은 결코 없습니다.

`[VERIFIED]` `PoseCopy`는 **본 버퍼만** 복사하며 루트는 건드리지 않습니다.

## 낡은 사본: 유효해 보이지만 아닌 필드 세 개

`[VERIFIED]` `Skeleton+0x120`, `Skeleton+0x250`, `owner+0x050`은 모두 같은 상위 엔티티
위치의 낡은 사본입니다. `Skeleton+0x120`은 프레임마다 돌지 않는 리셋/텔레포트 경로에서만
참조됩니다.

**이 중 어느 것에서도 렌더러로 이어지는 코드 경로가 없으므로, 여기에 값을 쓰는 것은 구조상
보이지 않습니다.** 그중 하나가 포즈 루트와 비트 단위로 동일하다는 것을 관측하더라도, 그건
출처가 같다는 뜻이지 그 필드가 루트에 값을 공급한다는 증거가 아닙니다.

이걸 확인하는 데 실제 시간이 두 번 들었습니다. 되풀이하지 마세요.

## 쓰기 창과 락

본을 바꾸고 엔진이 그 값을 쓰게 만들려면, 그 창은 좁고 구체적입니다.

- **너무 이르면**(애니메이션 솔버 이전) 쓴 값이 덮어써집니다.
- **너무 늦으면**(소비자 이후) 아무 효과가 없습니다.
- 부착된 객체의 경우, 올바른 시점은 **`Skeleton::PublishAttachments` 진입 지점**입니다.
  엔진이 각 부착 객체의 월드 트랜스폼을 포즈에서 합성한 뒤 배치하는 곳이 바로 거기입니다.

`[VERIFIED]` 이 전체 시퀀스는 엔진 워커 스레드에서 스켈레톤 락(`skel+0x1F0`) 아래
실행됩니다. 다른 스레드에서 동기화 없이 고빈도로 쓰면 경쟁이 발생하고 `movaps` 쌍이 찢어질
수 있으므로, 여기서는 대충 해서는 안 됩니다.

`[VERIFIED]` 포즈 루트에 쓴 값은 **부착 객체에서는 살아남지 못합니다.** 부모의 어태치먼트
퍼블리시가 트랜스폼 변경 알림을 통해 자식의 포즈를 dirty로 표시하고, 일곱 개 명령어 뒤에
인라인으로 `PoseRefresh`를 호출해 두 루트를 모두 다시 도출하기 때문입니다.

## 의도적으로 남겨 둔 정정

리그의 다섯 번째 초기화 패스를 앞서 해석했을 때는, 포즈 버퍼가 **노드마다 4x4 행렬 두
개를 스트라이드 0x80으로** 담는다고 결론지었습니다. 그 해석은 초기화 코드의 "단위"를
4바이트로 보았습니다.

**틀렸습니다.** 단위는 1바이트이고, 스트라이드는 `{float4 T, float4 Q}`로서 `0x20`입니다.
`GetBoneRecord`의 `shl rax, 5`는 모호할 여지가 없습니다.

같은 실수에서 파생된 정정 두 가지:

1. 캐릭터별 포즈 버퍼 포인터는 인스턴스 풀 슬롯에 있지 **않습니다.** `Pose+0x178`입니다.
2. "rig+0x430에 애니메이션되는 4x4 행렬이 있고 +0x470에 사본이 있다"는 런타임 관측은
   `0x20` 스트라이드와 맞지 않으며, 어떤 것의 증거로도 이어서 쓰면 안 됩니다. 그것은 힙에서
   리그 근처에 할당된 포즈 버퍼였지 리그 자체가 아니었습니다.
